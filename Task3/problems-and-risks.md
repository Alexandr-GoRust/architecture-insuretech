# Task3 — Переход на Event-Driven архитектуру: проблемы и риски текущего решения

## Контекст

Сейчас core-app и ins-comp-settlement держат локальные реплики данных о продуктах
и тарифах и обновляют их опросом (polling) REST API сервиса ins-product-aggregator:

- core-app запрашивает обновления раз в 15 минут;
- ins-comp-settlement — раз в сутки (ночью, при формировании реестра оформленных страховок);
- дополнительно ins-comp-settlement раз в сутки по REST тянет из core-app все оформленные за день страховки.

InsureTech планирует подписать агентские соглашения ещё с пятью страховыми
компаниями (станет 10 вместо 5).

## Проблемы и риски текущей архитектуры

### 1. Кратный рост времени ответа агрегатора и его деградация

ins-product-aggregator на каждый вызов синхронно опрашивает все страховые
компании и лишь затем отдаёт агрегированный список. С удвоением числа СК
(5 → 10):

- время ответа агрегатора станет равно времени ответа самой медленной из
  уже десяти компаний (синхронный fan-out);
- вероятность упереться в таймаут хотя бы одной СК за один вызов вырастет
  кратно — а это ошибки и ретраи для всего списка целиком;
- RPS на API каждой страховой компании вырастет пропорционально числу
  потребителей-реплик (каждый экземпляр core-app опрашивает сам за себя).

**Риск:** отказ одного «медленного» партнёра блокирует обновление данных
о тарифах для всего продукта.

### 2. Рассинхронизация реплик (данные устаревают на интервал опроса)

- core-app может работать с тарифами, устаревшими на 15 минут; расчёт
  стоимости страховки по устаревшему тарифу — прямые финансовые потери
  и жалобы;
- ins-comp-settlement — с данными, устаревшими на сутки: раз в месяц
  реестр взаиморасчётов может быть сформирован по тарифам «вчерашнего дня»;
- при сбое одного из циклов опроса (ошибки REST, недоступность агрегатора)
  расхождение накапливается неограниченно долго — реплика может «залипнуть»
  на данных, которым несколько дней.

### 3. Пиковая нагрузка «все сразу» (стадо)

Все экземпляры core-app опрашивают агрегатор по расписанию. При росте числа
реплик (масштабирование под нагрузку, HPA) они синхронно создают всплеск RPS
на агрегатор и далее — на API всех СК. Ночной запрос ins-comp-settlement
«все оформленные за день страховки одним вызовом» — тяжёлый отчётный запрос
к БД core-app в один момент: пик потребления ресурсов именно тогда, когда
идёт формирование реестра.

### 4. Жёсткая связанность доступности

Синхронные цепочки core-app → ins-product-aggregator → СК и
ins-comp-settlement → core-app / агрегатор: недоступность любого звена
ломает процесс целиком (недоступен агрегатор — не оформятся страховки,
хотя core-app и его реплика данных живы).

### 5. Хрупкость суточной батч-интеграции settlement → core-app

Разовые большие синхронные выгрузки за день: таймауты на больших объёмах,
повтор полной выгрузки при любом сбое в середине (нет позиционности),
невозможность incremental-доставки.

## Целевое решение (кратко — детали на диаграмме)

1. **Продукты и тарифы → Event Streaming через брокер (Kafka):**
   ins-product-aggregator публикует поток событий об изменении продуктов и
   тарифов (топик `insurance-products`); core-app и ins-comp-settlement
   подписаны на поток и актуализируют свои реплики по факту изменения.
   Итог: задержка реплик — секунды вместо 15 минут/суток; нагрузка на СК
   не растёт с числом потребителей (каждый публикуемый факт читается всеми
   подписчиками из одного топика).
2. **Оформленные страховки → поток событий:** core-app публикует событие на
   каждую оформленную страховку (`policy-issued`); ins-comp-settlement
   накапливает их у себя и формирует реестр из локальных данных — суточный
   REST-запрос исчезает вместе с пиком.
3. **Transactional Outbox — да, применяем:** публикация событий (и в
   core-app, и в ins-product-aggregator) идёт через outbox-таблицу в той же
   транзакции, что и бизнес-изменение, с вычиткой CDC (Debezium) в Kafka.
   Это исключает двойную запись и потерю событий при сбое между коммитом БД
   и публикацией.
4. Декомпозиция функциональности между сервисами не меняется (по условию);
   меняется способ доставки данных: REST-polling → подписка на события.
